142. ## Threading Model
143. 
144. The plugin uses Python's `asyncio` event loop (provided by DeckyLoader) as the primary concurrency mechanism:
145. 
146. - **RPC handlers** — `async def` coroutines called by DeckyLoader when the frontend invokes `callable()`
147. - **Connection accept loop** — `asyncio.Task` running `_accept_connections()` that awaits L2CAP socket accepts
148. - **Input read loop** — `asyncio.Task` running `_read_loop()` that uses `evdev.async_read_loop()` for non-blocking event reads
149. - **Config persistence** — `threading.Lock` protects the `Config._data` dict since config can be read from the async context and written from any thread
150. 
151. No additional OS threads are spawned. The `evdev` async reader and socket operations all run on the single asyncio event loop.

172. ## Security Model
173. 
174. - **Root privileges** — the plugin runs with root access (set via `"flags": ["root"]` in `plugin.json`). Required for `EVIOCGRAB`, `hciconfig`, `systemctl`, and binding L2CAP sockets on privileged PSM ports (<1024).
175. - **EVIOCGRAB** — the controller device is grabbed exclusively to prevent input events from reaching Steam while broadcasting. Released on stop.
176. - **Bluetooth pairing** — uses `NoInputNoOutput` agent capability (no PIN exchange). This prioritizes ease of use over pairing security. The BT device class and SDP record identify the device as a gamepad, reducing social engineering risk.
177. - **No network access** — the plugin does not make any HTTP/internet requests. All communication is local Bluetooth.
178. 
179. ## Future Considerations
180. 
181. - **Rust HID daemon** — replacing the Python input→HID→L2CAP path with a Rust binary could reduce latency by eliminating GIL contention and Python's asyncio overhead. The Rust daemon would read evdev, pack reports, and write to L2CAP sockets in a single tight loop.
182. - **BLE HID** — Bluetooth Low Energy HID over GATT would enable connections to more devices without Classic BT pairing, but iOS GameController framework support for BLE HID gamepads is limited.
183. - **Multi-connection** — supporting multiple simultaneous connections would require multiplexing HID reports across separate L2CAP socket pairs, plus managing multiple accept loops.

225. - `NoInputNoOutput` pairing is supported — iOS auto-pairs without a PIN dialog

227. Games must adopt the `GCController` API to receive gamepad input. Most modern iOS games support this. The system-level Game Controller settings UI shows paired controllers.

230.

232. 
233. - No app-side changes needed — the system interprets HID reports as `InputDevice` events
234. - Device class `0x002508` causes Android to display the device as a gamepad
235. - Works with all apps that use standard `KeyEvent`/`MotionEvent` for gamepad input
236. - Some Android versions may request pairing confirmation even with `NoInputNoOutput` — this is a one-time dialog

239. 
240. Windows recognizes the HID report descriptor and maps it to `XInput` or `DirectInput`:
241. 
242. - Appears as a standard gamepad in the "Game Controllers" control panel
243. - Works with Steam's controller support, Xbox Game Bar, and most PC games
244. - Windows may install a generic HID gamepad driver on first connection (takes a few seconds)

246. ## Latency Analysis
247. 
248. End-to-end latency from physical button press to host-side event:
249. 
250. | Stage | Typical Latency | Notes |
251. |-------|----------------|-------|
252. | Controller hardware → kernel | < 1 ms | USB HID polling interval on the internal bus |
253. | evdev read (`async_read_loop`) | ~0.5 ms | Async read from `/dev/input/eventN` |
254. | Deadzone + state update | ~0.01 ms | Bitwise operations and integer comparisons |
255. | `pack_report()` | ~0.01 ms | `struct.pack` of 14 bytes |
256. | Python → L2CAP `send()` | ~0.5 ms | Kernel socket buffer copy |
257. | Bluetooth radio transmission | 5–10 ms | BR/EDR link with adaptive frequency hopping |
258. | Host HID driver processing | ~1 ms | Varies by OS and driver |
259. | **Total** | **~7–13 ms** | Imperceptible for most game genres |
260. 
261. The dominant factor is the Bluetooth radio hop. Actual latency depends on RF conditions, host Bluetooth stack implementation, and connection interval negotiation.

263. ## Troubleshooting
264. 
265. ### Device not discovered
266. 
267. - Verify `bluetoothd` restarted with `-P input`: check `ps aux | grep bluetoothd`
268. - Confirm adapter is discoverable: `bluetoothctl show` should list `Discoverable: yes`
269. - Check device class: `hciconfig hci0` should show class `0x002508`
270. - Ensure no other application has grabbed the BT adapter
271. 
272. ### Pairing fails
273. 
274. - Reset the agent: `bluetoothctl agent off` then `bluetoothctl agent NoInputNoOutput`
275. - Remove stale pairing on both devices and retry
276. - On iOS: go to Settings → Bluetooth → tap (i) next to the device → Forget This Device
277. 
278. ### Connected but no input
279. 
280. - Verify evdev device is found: check DeckyLoader logs for `"Found controller:"`
281. - Confirm device is grabbed: `"Grabbed device exclusively"` should appear in logs
282. - Test L2CAP sockets: the interrupt channel client (`_interrupt_client`) must not be `None`
283. - Send a test: look for `"Failed to send HID report"` errors in logs
284. 
285. ### High latency
286. 
287. - Reduce polling rate from 500 Hz to 250 Hz if the Bluetooth stack is congested
288. - Move closer to the target device to reduce RF retransmissions
289. - Check for 2.4 GHz Wi-Fi interference — Bluetooth shares this band
290. 
291. ### bluetoothd won't restart
292. 
293. - Check if another process holds a lock: `fuser /var/run/dbus/system_bus_socket`
294. - Verify the binary exists: `ls -l /usr/lib/bluetooth/bluetoothd`
295. - Manual restart: `sudo /usr/lib/bluetooth/bluetoothd -P input --nodetach &`
